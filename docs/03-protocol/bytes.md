# 03-1 · 字节、大小端与协议帧

后端经常直接使用 JSON 对象；上位机面对设备时，必须先读懂**比特与字节的契约**。

## 十六进制和字节

`0xFF = 255`，一个字节能表示 0～255。两个字节可表示无符号 `ushort` 的 0～65535；如果按有符号的 `short` 解读，范围为 -32768～32767。**同一段字节按不同数据类型解释，含义可能完全不同。**

## 大端与小端

假设设备发送：

```text
01 2C
```

- 大端（高位字节在前）：`0x012C = 300`。
- 小端（低位字节在前）：`0x2C01 = 11265`。

明确字节序，不要在未验证协议文档时直接使用 `BitConverter.ToInt16()`（其结果依赖主机体系结构的字节序）。

C# 解析网络大端无符号 16 位整数：

```csharp
using System.Buffers.Binary;

ReadOnlySpan<byte> bytes = stackalloc byte[] { 0x01, 0x2C };
ushort raw = BinaryPrimitives.ReadUInt16BigEndian(bytes);
double temperature = raw / 10.0; // 文档明确规定 0.1 ℃/单位才这样算
```

## 帧格式：数据不只是温度值

设备可能定义：

```text
帧头  地址  命令  长度  负载   校验
AA55   01    03    02   012C    CRC
```

要按设备手册依次处理：识别帧头、检查长度、校验完整性、再解码负载。**CRC 用于检出传输错误，不提供加密或身份认证。**

TCP 是字节流，即使发送端一次 `Write` 了 20 字节，接收端也可能拆成多次 `Read`；或者两帧合并成一次 `Read`。

## 为什么课里的模拟器用换行分帧？

初期示例采用 UTF-8 文本行：

```text
TEMP=23.5;PRESSURE=101.2;RPM=1200\n
```

以 `\n` 作为结束符，便于用 `ReadLineAsync` 实现**正确的消息边界**。后续学 Modbus TCP 时，改用 MBAP 头里的长度字段分帧，不能继续直接按文本行读。

## 练习与验收

1. 解析十六进制 `FF 9C`：按大端有符号 `short` 是 **-100**；如果设备单位是 0.1 ℃，代表 **-10.0 ℃**。
2. 思考四字节 IEEE 754 `float` 的字节顺序为什么不能想当然（某些设备还存在寄存器字序交换）。
3. 设计“长度不合法时丢弃一帧并记录异常”的错误处理流程。

**验收：** 能从十六进制报文算出值，并解释为什么必须确认类型、字节序和缩放比例。
